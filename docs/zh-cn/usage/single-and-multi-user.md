# 单人与多人部署

无论这个实例只有你一个人使用，还是要给整个组织接入，AgentTeams 都只有**一套部署模型**。安装时没有"单人模式"或"多人模式"可选：平台只安装一次，之后接入多少真人，改变的是**谁能做什么**，而不是系统怎么部署、怎么升级、怎么运维。

本页说明哪些东西始终不变、接入更多人时什么会变，以及各个角色分别处在什么位置。

## 一句话结论

- **同一套安装、同一条升级路径、同一套存储布局、同一套 API。** 一个人和五十个人用的是同一个部署。
- **每个 Team 必须恰有一个 Leader。** controller 会拒绝 `workerMembers` 中 `team_leader` 数量为 0 或多于 1 的 Team，因此团队协调、团队记忆播报与事件转述始终有归属。这是**每个 Team 的约束**，不是安装级要求：一个安装可以完全没有 Team，独立 Worker 也是允许的。推荐的默认拓扑（Leader + Worker，Manager 可选）是建议，不是约束。
- **Manager 是可选的。** 它把 controller API 与 CLI 操作翻译成 admin DM 里的对话，且**仅 L1（管理员）**可用。部署可以不装它——dashboard 与工作台插件覆盖点选式运维（前提与缺口见下文 Manager 一节）。
- **个人记忆属于这个真人，不属于 Manager。** 它按人存放、经 controller API 访问，因此装不装 Manager 都一样（设计提案 — #1412；尚未可用）。
- **接入一个人是资源变更，不是部署变更**：创建 Human、授予权限级别、把这个人加进团队。

## 提案，尚未可用

以下能力是**设计提案，尚未可用**，不属于本版本行为：

- 按人文件区、文件 API、回收站与配额 — issue #1414（实现 PR #1426，open）。
- 按人记忆锚点 — issue #1412（V16 pending）。
- 团队事实（team facts）写入路径 — issue #1412 第二阶段。

这些是设计，不是本版本的行为；本文档其余部分只描述今天可用的东西。在它们落地之前，请把个人记忆视为**尚未可用**，而不是"由某个 Manager 拥有"。

## 角色

| 角色 | 是否必需 | 职责 |
|---|---|---|
| **Controller** | 必需 | 平台层：资源、容器、存储、权限、网关配置 |
| **Leader** | **必需——每个 Team 恰有一个 Leader** | 团队面协调：任务分解、分配、团队记忆播报、事件转述。每个 Team 内部必需；不是安装级要求 |
| **Worker** | 按需 | 执行具体任务，拥有自己的模型、runtime、技能与 MCP 配置 |
| **Human** | 至少一个 | 设定目标、观察进展、随时介入；每个真人有一个权限级别和各自的作用域 |
| **Manager** | **可选** | 面向 L1 的对话式运维：通过对话创建与管理资源 |

> “必需”描述的是 controller 强制执行的范围，不是部署形态：Leader 要求作用于**每个 Team 内部**（`workerMembers` 恰有一个 `team_leader`）。Team 本身可选，独立 Worker 允许存在；“可选”（Manager）表示 controller 既不要求也不禁止。详见下文“当前的强制方式”。

Controller 是平台层，Worker 是你按需实例化的执行单元；Leader 是**每个 Team 内部**的要求。真人与 Manager 是在一个已运行的部署上追加的。

## 只有一个人时怎么用

1. 照常安装 AgentTeams（本地或 Kubernetes），保持推荐的默认拓扑（Leader + Worker）。
2. 创建这个人：
   - **管理员（L1）**身份负责管理部署。L1 真人与其他人一样拥有 Matrix 账号；其管理类 API 操作使用 admin 凭据，而 L2/L3 真人用自己的 Matrix token 认证；
   - **团队成员（L2）**身份的作用域是 `accessibleTeams` 中列出的团队。
3. 把这个人加入要干活的团队（团队成员关系与 `humanMembers`）。
4. 在团队房间里协作：真人提出目标，Leader 拆解并分配，Worker 执行，真人在同一个房间里跟踪并介入。
5. 如果管理员需要对话式运维，再按需安装 Manager。

这条流程里没有任何"单人变体"——十个人也是同一套顺序。

## 有多个人时怎么用

一个人一个人地加进来即可：不重装、不切换模式。

| 权限级别 | 适合谁 | 能做什么 |
|---|---|---|
| **L1**（管理员） | 部署所有者 / 平台运维 | 管理实例、全部资源与全部真人；也是唯一能使用 Manager 对话式运维的级别 |
| **L2**（团队作用域） | 工程师、分析师、评审人 | 在 `accessibleTeams` 列出的团队内工作；可选能力可扩展特定界面 |
| **L3**（Worker 作用域） | 只需要读某个 Worker 产出的人 | 对 `accessibleWorkers` 中列出的 Worker 只读 |

实际操作规则：

- **一人一个 Human 资源。** 显示名、身份源、权限级别都挂在上面；这个人的作用域随之确定。
- **访问跟随成员关系。** 个人的工作区在自己的命名空间，并默认对该人所属团队共享；记忆仍是个人锚点（两者均为提案——见"提案，尚未可用"）。团队内容留在团队前缀里，真人之间读不到对方的工作区，一个人也只能看到被授予的团队与 Worker。
- **团队与真人独立扩展。** 某个群体需要自己的 Leader 与 Worker 时，加一个团队；一个人可以属于多个团队。
- **房间跟随成员关系。** 每个团队有自己的房间；一个人会加入其所属团队的房间。
- **移除一个人**会移除其成员关系与访问权。删除其存储数据是另一个显式动作——移除不等于删除。

## 始终不变的部分

| 领域 | 一个人和多个人的共同点 |
|---|---|
| 安装 | 同一条安装路径：本地或 Kubernetes，同一套 values 与 CRD |
| 升级与 runtime 切换 | 同一套升级流程、同一套 runtime 适配器、同一套回滚 |
| 存储布局 | 同一套对象存储前缀；按人作用域是增量，不是另一套部署 |
| API | 同一套 controller API；按人资源只是实例更多 |
| 权限 | 同一套 L1/L2/L3 模型，按请求逐次判定 |
| 运维 | 同一套日志、审计、备份与迁移流程 |

## 接入更多人时会变的部分

| 领域 | 变化 |
|---|---|
| Human 资源 | 更多 `Human` 对象，各自带级别、团队与能力位 |
| 团队成员关系 | 更多团队房间与成员关系；`humanMembers` 与 `accessibleTeams` 变多 |
| 权限矩阵 | 更多主体需要评审；能力位按人授予 |
| 个人数据 | 更多按人工作区（对所属团队共享）与记忆锚点（个人）——提案，尚未可用（见"提案，尚未可用"） |

## Manager 在单人 / 多人部署中的位置

**预期模型。**

- **每个 Team 必须恰有一个 Leader**（按团队强制，见下文“当前的强制方式”）；**Manager 可选**——L1 运维的便利层，不是执行依赖。推荐的默认拓扑（Leader + Worker，Manager 可选）是建议而非部署约束：一个安装可以没有 Team，也可以只有独立 Worker。
- **仅 L1。** 只有管理员使用它的对话面；L2 与 L3 真人通过 dashboard、工作台插件与自己的作用域工作。
- **它的记忆是运维记忆。** 建过什么、事故、运维历史——存在它自己的 agent 前缀与 `manager/*` 下。它永不拥有、也不写入某个真人的记忆。

**当前的强制方式，以及缺席时由什么覆盖。**

- **Leader——按 Team 强制。** 创建或更新 Team 时，controller 校验 `workerMembers` 中恰有一个 `role=team_leader` 的成员，0 个或多个都会被拒绝。它不要求安装中存在 Team，也不限制独立 Worker。
- **Manager——不强制。** controller 中没有任何机制要求或禁止 Manager；部署缺省即可无 Manager 运行。
- **无 Manager 时覆盖的是：** dashboard 与工作台插件覆盖**声明式资源与只读运维面**——创建/编辑资源、查看状态、跟踪团队工作。前提是所装 controller 版本与工作台插件提供这些界面。
- **未覆盖的：** 对话式运维、部分跨资源流程、升级/迁移编排，仍需 Manager 或直接 controller API/CLI。这些替代路径未在当前文档版本中逐项验证。
- 如果你移除 Manager，请先复核此前依赖的运维流程，再认为点选式界面足够。

## 个人工作区与个人记忆（提案设计）

本节内容当前均不可用。

它们跟着真人走，不跟着 Manager 走：

- 布局：`humans/<human>/files/`（**工作区**）、`humans/<human>/memory/` 与 `humans/<human>/digest/`（长期记忆）。
- 默认访问：本人与其**所属团队**（Leader 与 Worker）对 `files/**` 可读写——它是共享工作区，不是个人网盘；`memory/` 与 `digest/` 仍属个人。
- 写入：服务该真人的 agent 经 **controller API** 提交条目，由 API 归属到该人的作用域；本人经同一 API 读写自己的作用域，团队以团队身份写入工作区。
- 隔离：任何 agent（含 Manager）都不被授予 `humans/*` 的存储访问；作用域由 API 强制，非成员团队返回 404。
- 删除进入**远端回收站**（可恢复，默认保留 30 天）；同步按设备开启，并只作用于用户选中的文件夹。

## 常见问题

**只有一个人时，需要选一种部署模式吗？**
**当前：** 可用。无需选择部署模式——安装一次即可；接入多少真人是资源决策，不是安装选项。

**可以没有 Leader 吗？**
**当前：** 可以——只要你没有运行 Team。安装中可以完全没有 Team，独立 Worker 也是允许的。不可能的是“没有 Leader 的 Team”：**每个 Team 必须恰有一个 Leader**——`workerMembers` 中 `team_leader` 数量为 0 或多于 1 的 Team 会被 controller 拒绝（见 Manager 一节）。

**可以没有 Manager 吗？**
**当前：** 可用。dashboard 与工作台插件覆盖声明式资源与只读运维面（前提与缺口见 Manager 一节）；Manager 只是给 L1 多一个对话面。

**不装 Manager，个人记忆放在哪？**
**当前：** 不可用——按人记忆是设计提案（#1412）。落地后：按人命名空间，经 controller API 访问——不依赖 Manager。

**一个人可以属于多个团队吗？**
**当前：** 可用。团队成员关系与 `accessibleTeams` 定义作用域；一个人可以在多个团队里工作。

**L2 与 L3 真人做的事情一样吗？**
**当前：** 可用。L2 是团队作用域、能在团队内工作；L3 只读，且限于分配给它的 Worker。

**接入更多人会改变升级或备份流程吗？**
**当前：** 可用。流程不变，只是需要纳入更多按人资源。
