## 一、问题与验收目标

本轮验证发现任务路径重复拼接、执行目录不一致、本地文件未同步、工具 schema
丢失、执行状态消息被错误接入模型等问题。应分别修正公共协议、公共实现与运行时
接入，禁止为某个 Leader/Worker 组合增加接收端例外。

目标：Agent 不拼共享存储路径，不编辑任务元数据，不重复派发、同步或通知。
正常 Worker 使用 begin 与 submit 两次协作操作；运行时已提供有效 begin 收据时只需
submit。实际业务工具、必要的检查点与异常处理不计入这两次操作。

成功必须同时满足：真实执行、准确产物、Leader 验收、原请求会话收到正确回报。
任务状态 completed、工具返回成功或聊天声称完成均不能单独证明交付成功。

首期沿用文件后端；数据库迁移属于后续存储实现，不在本次直接引入数据库。

## 二、当前实现与收敛边界

- TeamHarness 提供 taskflow、filesync、公共角色与任务技能。
- ack_task 已拉取任务说明和依赖输入，submit_task 已合并同步、提交和通知。
- Controller 提供身份验证、任务元数据条件提交、持久化协作通知与恢复接口。
- 部分生命周期逻辑仍读写本地 meta.json 并同步对象存储；目前尚非存储无关实现。
- filesync 与 deliverables 仍暴露 shared/tasks/...，Agent 仍可能错误拼接。

Project 归属、Team 作用域与原始回复路由属于可信任务上下文，不是 Agent 需要猜测的
参数；Bucket、存储前缀和后端位置属于公共部署配置。两类信息均由公共层解析。
公共工具 schema、角色提示词与文件技能必须随新接口同步收敛，停止要求 Agent 拼接
任务路径或为了取文件创建 Project。安装/启动阶段验证协议能力并注入匹配的公共
说明；不能只删除提示词里的参数，而让旧接口继续要求 Agent 填写这些参数。
完整命令可用前不得在运行时宣称 begin/submit 等新接口已经实现。

只改提示词或给旧 MCP 动作增加 CLI 别名无法解决存储耦合。推荐由公共任务服务提供
操作语义，CLI 和 MCP 调用同一实现，运行时仅连接原生模型、工具和本地目录。
迁移现有规则时保留所有权限、状态门禁、检查点与提交版本校验，不复制第二套规则。

## 三、公共命令契约

### 1. 生命周期

| 命令 | 操作者 | 合并执行的行为 |
|---|---|---|
| task create | Manager | 登记原始请求、绑定 Leader/请求路由、排队交接事件 |
| task plan | Leader | 在原主任务保存完整执行计划、准备房间、派发可执行子任务 |
| task begin | 执行者 | 校验执行归属、ACK、准备输入与工作目录、返回恢复上下文 |
| task submit | 执行者 | 验证指定文件、上传、保存候选提交、排队通知 Leader |
| task accept | Leader | 绑定精确 submissionId、机械校验、记录业务验收、推进依赖 |
| task reject | Leader | 绑定精确 submissionId、记录拒绝原因，执行现有返工规则 |
| task complete | Leader | 验证主任务完成条件、持久化最终报告、排队回告原会话 |
| task get | 有权限的调用方 | 返回当前任务、依赖、提交和产物的聚合视图 |

普通问答不创建任务；Project 仅在明确需要时单独使用。create 不替 Leader 分解任务；
plan 沿用 Manager 已登记的主任务 ID。拒绝结果不隐式重开 terminal revision 任务。
返工必须沿用公共生命周期允许的替代执行方式，不能私自换主任务或绕过终态。

begin 返回任务说明、验收标准、输入引用及必要预览、已准备的本地路径、输出/临时
目录与恢复检查点。运行时已准备的收据必须验证其执行身份，不能盲信旧缓存。
大文件按需获取；输入文本预览有大小上限并明确是否截断。

本地目录来自运行时提供的公共 shared 目录事实，不按 Harness 名称选择路径。
begin 自动准备已验收依赖的文件，版本变化或完整性校验失败不得返回准备成功。
新提交的依赖输入固定到已验收 submissionId 中的产物引用，不读取其他中间产物或后续
文件当前引用；缺失该确定版本时明确失败，不能回退到同名新文件。公共恢复上下文只返回
步骤、检查点版本和操作验证事实；已经保存结果的执行进入现有投递恢复，不重新开始业务。
本地输入副本为只读，输出和 scratch 单独定位。公共上下文携带 assignmentId、
generation 等身份事实供运行时校验，Agent 不需要手工复制这些字段来选择权限。

`task get` 的 `candidate` 返回当前提交的精确身份、业务结果状态、报告预览和提交时
选定的产物引用，不返回存储路径。报告预览最多 4096 字符，截断时带省略号及
`reportTruncated`；`reportFile` 提供不可变文件 ID 和版本，可通过 `task files read/get`
继续读取完整报告。报告引用不混入普通输出列表，也不会成为下游执行输入。产物来自
该提交的引用快照，缺失引用时不回退到同名当前文件；实际内容仍由读取及验收校验。

示例：

```sh
agt task begin T1
agt task submit T1 --summary "已完成分析并通过指定检查" --file report.md --file tests.log
agt task accept T1 --submission S1 --note "结果满足原始验收标准"
agt task complete MAIN --report "最终报告" --artifact A1 --artifact A2
```

submit 的 --file 相对于该 Task 的输出目录解析，不依赖当前 shell 目录。Agent 从
begin 获取实际本地目录进行业务工作。不得上传整个工作区或猜测应交付的文件。
复杂结果可使用本地清单文件，清单复用同一请求结构，不增加第二套提交语义。

提交事件携带摘要、检查证据、精确提交身份及产物引用，减少 Leader 重复查询。
accept 执行权限、当前版本和文件完整性检查，但不替代 Leader 的业务正确性判断。
不能通过减少工具调用来省掉独立验收。

#### 同一协议的 Agent 工具入口

公共 MCP `task` 将结构化参数转换为固定 `agt task ...` 参数数组，原样返回 CLI 结果，
不启动 Shell、不复制业务状态机。工具按照运行时角色展示操作：Manager 创建和读取，
Leader 计划、验收与完成，Worker 接单、提交和发布任务文件；最终权限仍由任务 API
校验。文件发布的 source 与 submit 的 files 都相对于准备好的本 Task 输出目录解析，
下载返回默认输入位置，Agent 不设置进程环境、Project、远端路径或任意下载目标。

创建来源不在模型可见 schema 中。框架在当前原生调用中带入真实事件、会话和人类身份，
桥接层仅为这一次 CLI 子进程设置来源环境，不改共享进程环境；模型提交私有来源字段会
被原生 schema 拒绝。Task 工具错误使用 MCP isError 返回，不把失败或非 JSON 输出注入成功回执。

QwenPaw 的受限验收/关闭会话保留该任务工具，继续移除通用 Shell 和修改产物的工具。
仅这个固定 Task 能力沿用已授权的任务系统权限，不再次索要工具授权；其他 MCP/文件/
Shell 权限策略保持原样。公共收据识别代码对 MCP 与 CLI 输出使用相同规则，事实进入
当前原生工具结果，不要求模型解释后再记忆。

桥接层将当前工具的 W3C traceparent/tracestate/baggage 仅传入本次 CLI 子进程，CLI
向公共任务 API 转发该关联信息，不覆盖显式请求头；不让 Agent 复制 Trace ID，也不
依赖共享进程环境保存某个会话的追踪上下文。真实 Langfuse 完整覆盖仍须在实际认证中验证。

隔离测试已通过真实原生 MCPTool、受限会话钩子与候选 CLI 验证验收/关闭、创建来源注入、
私有来源字段拒绝及权限范围；独立 stdio 协议测试验证公共服务器注册与 CLI 调用。
模型与任务 API 为确定性替身，不能据此声称完成实际 Harness 任务认证。

plan 使用 `POST /api/v1/tasks/{id}/plan`，CLI 支持 `--file plan.json` 或 `--json JSON`，
两种输入共享同一请求结构；每次调用仅请求一次公共任务操作。例如：

```json
{"nodes":[
  {"id":"A","title":"读取账单","assignedTo":"worker-one","spec":"实现账单解析模块","dependsOn":[]},
  {"id":"B","title":"读取退款","assignedTo":"worker-two","spec":"实现退款解析模块","dependsOn":[]},
  {"id":"C","title":"集成验证","assignedTo":"worker-one","spec":"使用已验收的两个模块完成集成","dependsOn":["A","B"]}
]}
```

node 的 id 是主任务内的局部步骤名，最多 50 个节点；执行 Task ID 由任务系统生成，
从返回的 nodes 中读取，不手工拼接。依赖只引用本计划局部步骤名，循环、缺失、重复
依赖及同名步骤均在任何房间/派发操作前拒绝。assignee 必须解析到同 Team 的注册
Worker，不能将 Leader 分配为自己的执行者。原始需求、Project 归属、路由、房间和
派单身份从已登记主任务继承，不作为 Agent 输入参数。

完整计划和全部节点说明先写入主任务；相同计划重试复用 planId，重排节点/依赖和同一
成员的注册别名不改变身份，改变工作内容不会覆盖既有计划。任务房间使用既有 Matrix
别名幂等机制，并核对 task/plan/Team/Leader 的所有权；创建响应丢失后解析同一房间。
保留 Team 管理员（包括仅提供名字的管理员及全局管理员回退）、合资格 Human 邀请及
接受邀请的现有机制，不把无权限 Human 加入执行房间。

派发先保存 prepared 执行记录和通知意图，再使用现有公共队列入队；主任务节点和
整体 assigned 状态保存后才允许执行记录变为 assigned。中间任一步骤退出，由现有
恢复扫描沿同一 Task/plan/delivery 身份继续，不生成第二次业务执行。Worker ACK
同步主任务阶段及该节点的 in_progress 状态。只有依赖节点及其实际候选均验收通过，
才准备后继执行。每次投递前重新检查执行冻结与可选 Project 活动状态。

plan 和 accept 返回实际记录的 assignments 收据，pending/queued 与执行、验收、
交付成功分别表达。公共回执代码生成通知事实，QwenPaw 原生工具上下文绑定任务系统
确认的主任务或精确候选；handoff 消息自行声明的 Task ID 不能扩展操作范围。
协议测试已覆盖从计划、并行根节点、精确候选验收到依赖推进和最终完成的接口链路，
以及房间创建丢响应、队列中断、入队后激活失败、冻结恢复及非法所有权。
这些接口/SDK 替身测试不是实际 Harness 认证。

accept/reject 使用 `POST /api/v1/tasks/{id}/accept` 或 `/reject`，仅接收
`submissionId` 和 `note`；主任务、所属 Team、可选 Project 与通知目标从任务系统解析。
note 是 Leader 对业务正确性的检查证据或退回原因，机械校验不能替代该判断。
accept 合并记录业务验收和原有 passing review，校验不可变候选的摘要、报告指针、
产物内容、成功状态、独立 Leader 身份与 r1 的可信人类批准，不能靠 display 字段伪造批准。
reject 不受尚未完成的人类批准或执行冻结阻拦；成功候选退回到 revision，BLOCKED/
INTERRUPTED 候选按已有规则落到 blocked，均保持终态，不重开旧执行。

决定先在执行任务内与终态一起 CAS 保存，使用不透明 review ID；同一决定重试复用
收据，改变候选、接受/拒绝或 note 会被拒绝。主任务只合并该节点的确定候选决定，
使用 CAS 保留其他节点的并发进度。父任务写入中断时返回 `mainProjection=pending`，
现有恢复扫描从已保存决定继续，正向推进仍检查主任务/Project 的冻结与活动状态。
全部节点验收完成后，主任务投影与 `main_task_ready` 待通知意图一起保存，沿用原有
公共通知队列。当前公共 get 返回 resultStatus 和 review；QwenPaw 对精确当前候选的
最终 CLI 工具回执生成上下文事实，不把状态同步 pending 写成已通知或已交付。

### 2. 文件与产物

```sh
agt task files list T1
agt task files read T1 --name report.md
agt task files get T1 --artifact A1
agt task files put T1 --source ./analysis.csv --name analysis.csv --kind intermediate
```

- list 返回已登记的输入、中间产物与交付物；不靠扫描存储目录推断正式交付物。
- read 返回受限文本、版本和截断信息；分段续读固定同一版本。
- get 准备并校验文件，返回当前执行环境实际可读的 localPath、版本、大小和摘要。
- put 显式发布中间产物并返回稳定引用，不提交或完成任务。
- name 是任务空间内的相对名称；拒绝绝对路径、越界与同名歧义。
- 任务逻辑身份包含 Team 作用域。身份上下文可唯一确定时自动使用；有歧义必须明确。
- 产物引用绑定确定版本；上游输入默认只读，本地临时文件不自动成为共享产物。
- begin 已准备的输入不重复获取，submit 的最终文件不要求提前 put。
- 凭据、Bucket、对象键与元数据文件路径不进入 Agent 的必填参数。

### 3. 状态、失败与通知

任务状态、执行轮次状态、通知投递状态分别表达。运行时一轮 completed 不代表任务
已验收。普通对话、协作控制、进度与 Stop/Steer 按统一结构分类。
执行状态 m.room.message 必须携带 m.notice、com.agentteams.execution 和
org.agentteams.progress_only=true；不允许针对某种 Harness 推断缺失字段。

每条命令返回固定 JSON 契约，区分操作提交结果、当前状态/版本、收据、通知状态、
下一步动作与结构化错误。稳定错误码至少覆盖文件缺失、旧提交、取消/重新分配、
权限不足、临时不可用和操作结果未知；错误提供是否可重试与允许的恢复动作。
下一步动作不能要求反复轮询；业务推进由持久化事件唤醒。

一个 CLI 调用可以执行多个内部请求；合并调用不等于文件与元数据具有跨系统事务。
先验证并持久化产物，再提交状态；失败返回可恢复的原操作身份。禁止文件上传失败
仍报提交成功。通知待送达需如实返回 queued，由公共通知机制重试。

#### 发送方如何知道任务系统已自动通知下一节点

直接复用任务操作的同步工具返回，不新增 Harness 回执 HTTP 接口，不额外发一条
Matrix 消息唤醒发送方。CLI/MCP 必须保留任务系统的结构化返回。框架在工具调用完成时
确定性识别回执，校验 taskId、操作/提交身份和通知状态，并通过当前会话的原生上下文
机制注入简短的任务系统事实；不依赖 Agent 自己解析 JSON 或推断是否已通知。
公共层负责校验与生成事实文本，Harness 只连接原生上下文机制。流式中间片段、
失败响应、其他任务及重复回执不能重复注入或改变通知状态。原始工具结果仍须保留，
注入内容不能伪造为 Agent 自己说过的话，不能造成第二次派发或额外模型唤醒。Agent 面向任务系统工作，不需要感知 Controller 或其他部署组件；
返回使用“任务系统已接管通知/已自动通知下一节点 xxx/xxx 已确认接单”等业务表述，
并以权威收据证明相应状态。所有 Harness 遵循同一工具结果契约；禁止把自己发出的
Matrix 消息重新伪装为用户指令来补上下文。

提交返回示例（ID 为示意）：

```json
{
  "task": {"id": "T1", "status": "submitted", "submissionId": "S1"},
  "notification": {"status": "queued", "eventId": "E1", "recipient": "leader-a"},
  "nextAction": "Task system has queued an automatic notification to \"leader-a\" for review. Do not resend the notification; wait for acceptance or revision."
}
```

- submitted 只表示候选结果已保存，不能宣称已完成业务验收。
- pending 表示待通知意图已和提交一起持久化，但尚未确认进入通知队列。
- queued 表示持久化队列已接管，不能宣称 Matrix 已接收或对方已接单。
- 实际投递及接单状态以公共协作收据和任务状态为准；必要时经公共查询获取。
- Agent 不因 pending/queued 手工补发；Controller 恢复未完成的通知入队并负责重试。

提交和通知意图在同一任务条件提交中保存；入队后再登记通知 ID。进程在两步之间退出，
恢复扫描沿用相同提交/通知身份补齐入队，不重复生成业务提交。工具响应丢失时，原调用
可重试：相同内容返回原 submissionId；已提交后的同内容文件重传只返回原产物引用，
不能改变文件当前引用或候选结果。变更提交内容必须经过明确的返工生命周期。

认证必须检查框架识别回执并将通知事实注入发送方当前上下文，且 Agent 不重复通知；单独验证 HTTP
返回或 CLI 标准输出不等于这项 Harness 行为已通过。目前公共接口/CLI 测试通过；
QwenPaw 原生 SDK 的隔离测试已验证最终工具回执进入下一次模型请求的工具上下文，
保留原始结果、不冒充 assistant 消息且不增加工具调用。真实任务中的通知行为仍随
QwenPaw、OpenClaw 的完整任务认证执行。

请求身份来自可信上下文。相同逻辑操作重试使用相同幂等身份；两个独立但文本相同的
请求不能被误去重。旧 assignment/execution/submission 不得影响新一轮任务。
产物内容引用仍按内容去重。CLI 在首次发起文件发布前生成内部 `Idempotency-Key`，
单次调用内的传输重试沿用该键和相同的内容，不增加 Agent 参数。Controller 将回执和
按文件名读取的当前引用一次提交：已成功发布的旧操作重试返回原产物引用，不改变当前
引用；新的发布操作可以将当前引用切回已有内容，其他内容仍可按历史引用读取。
长任务与外部副作用维持现有检查点和执行代际约束，不为缩短命令序列而删除门禁。

公共事件由任务系统根据已登记主任务或已保存计划确认 `task/v1`，不能由调用方自行
声明。QwenPaw 先核对公共通知回执的发送者、接收者、会话和任务/提交身份，再通过原生
Task 工具准备 `begin` 或 `get`，由公共校验器生成事实并绑定当前操作范围。新协议不会
读取 `/meta` 来准备普通接单/验收，也不回退到旧 ACK/check。启动恢复仍使用现有执行
代际门禁，确认活动执行后重新取得公共 begin 上下文；保存结果后的恢复不得重做业务。
验收快照不是业务通过证明。受限验收/关闭会话保留 Task 入口并移除 Shell/编辑工具；
新协议回合移除旧 flow/filesync 工具，加载同一公共 Task skill。共享角色提示词显式
区分新协议与已有旧计划，不按 Harness 配对选择业务协议。

### 4. 原始交付路由、派单身份与上下文

主任务使用 `agt task create --leader LEADER --title "原始需求" --spec "完整需求与验收标准"`
创建，Agent 不提供源会话或接收人参数。框架从当前经过验证的原生请求带入来源，CLI
向公共 API 传递该上下文。创建返回 sourceEventId、主任务和交接回执，框架核对当前
来源后生成任务系统上下文事实；不修改进程全局环境来传递并发会话的来源。

主任务创建时绑定原始 Human 会话、最终人类接收者、首跳派单 Agent 和请求事件。
后续执行任务继承该主任务身份，保留逐级派发关系；执行房间不是最终交付位置。
这些字段来自可信入口上下文，由任务系统保存为不可变 task_origin，并保护原始需求
和实际回告路由。创建操作复用原有交接队列：同一来源请求重试保留相同任务/通知身份，
不同原始事件即使内容相同也独立创建；同一原始请求改写需求不能覆盖已登记任务。
任务登记和待交接意图一起保存，队列暂时失败或进程退出后恢复扫描补齐交接。
人类来源会话和 Leader 接单 DM 分别定位，不将前者误作执行房间。

Leader 不填写接收人、会话地址或
派单 Agent 的账号，不从最近一条消息推断终态接收人。

Human 在会话 A 请求 Manager，Manager 派给 Leader 的场景：Leader 在任务房间验收
全部执行结果后，调用 `agt task complete MAIN --report "最终报告"`。任务系统以该
Manager 的身份把最终报告和确定版本的交付产物投回会话 A，不要求 Manager 再判断、
重新总结或调用消息工具。最终清单默认汇总全部已验收提交中明确声明的 output 文件，Leader 可用重复的
`--artifact` 指定需要交付的产物 ID。清单记录来源 Task、名称、大小、版本和摘要，
不会使用未验收的同名当前引用或 intermediate 文件。原始报告、产物引用、投递身份、
目标会话、操作身份固定后再入队；投递失败保留原操作重试，不重复生成主任务或更换接收者。

回告区分报告消息、文件展示和派单 Agent 上下文补齐的完成证据；报告发出但附件
失败，不能算完整交付成功。消息中应展示产物名称、来源、摘要/大小与实际可访问的
文件入口，不能只给共享目录路径或声称“文件已生成”。执行者临时文件与未验收的
中间文件不自动成为最终交付物，不能通过猜测最后一个 DAG 节点来选择最终文件。

Leader 当前会话通过完成操作的工具回执获知“已完成，任务系统已接管回告”。首跳
派单 Agent 的原会话应在实际投递后补入已发送报告、产物引用及消息回执；这是框架
的上下文事实同步，不是新的人类请求，也不能额外唤醒一次模型或重复转发。投递前
只能注入 pending/queued，不能提前写“已发送”。此异步事实沿用公共任务/通知收据，
不增加每种 Harness 独立的回执 HTTP 接口，不通过放开全部自发消息过滤来回填。

当前实现已验证：创建幂等、来源保护和交接中断恢复，原生创建工具带入来源和创建回执，
主任务门禁、已验收产物内容检查、报告不可变、完成与待回告意图
一起保存、原会话报告投递的去重与中断恢复，以及 QwenPaw 原生工具上下文回执。
原生 `m.file` 附件通过 `com.agentteams.attachment` 关联实际报告消息；上传与发送均
使用原派单 Manager 身份。报告及每个附件有稳定的 Matrix transaction ID 和独立
投递回执；部分文件失败不重复已成功项，也不把报告已发误判为完整交付。仍保留
原有产物发布检查，并在完成冻结前校验，避免完成后才发现文件不能交付。

HTTP 协议测试已验证媒体上传字节、发送身份、原始房间、附件关联及部分失败恢复；
派单 Agent 的上下文同步通过公共 `GET /api/v1/task-deliveries?roomId=...` 读取完成投递记录，
仅返回认证派单 Manager 在指定原始会话中已发出报告及全部附件的记录。报告正文在首次
发送前冻结，消息和文件回执均来自实际投递；旧记录缺少正文快照时不推测其发送内容。
读取不依赖创建回执是否成功到达，也不读取 Harness 私有历史或数据库。

QwenPaw 在原会话下一次真实人类请求进入时，通过原生上下文钩子补入事实，不额外
唤醒模型或调用消息工具。仅在原生推理阶段已接纳上下文后记录去重身份，并随原生
会话状态一起保存。查询支持分页；注入优先保留近期记录，总量限制为 16384 字符，
报告和附件列表截断时明确标注，未纳入的记录不确认消费。隔离原生 SDK 测试覆盖
无创建回执、报告及附件事实注入和会话恢复后的去重；真实 Matrix/客户端显示、
真实原会话中的状态持久化仍待验证，不能据此把完整交付链路或 Harness 认证标记为通过。

### 5. 存储与兼容

外部协议只定义任务资源、动作和不透明版本；不定义 meta.json 或数据库表。
本地任务文件是准备后的投影，不能作为状态修改入口。后端逐步收回元数据读取、
状态转换和提交权限。产物内容继续存对象存储；数据库可管理任务与产物索引。
文件后端与未来数据库后端必须通过同一测试，迁移保留任务、提交、产物和通知身份。

现有 MCP 调用分阶段接入同一公共操作实现，旧接口在兼容期保留，不新增运行时专用
协议。部署顺序与协议能力必须校验；缺少必需能力明确拒绝，不能静默接单。

## 四、收益估计与对照验证

以下是根据本轮失败类型提出的工程假设，尚非实测收益：

| 指标 | 首轮验证目标/预估 |
|---|---|
| 轻量多步骤协作任务端到端耗时 | 降低 20%–40% |
| 模型驱动的协作工具调用数 | 减少 30%–60% |
| 同条件任务交付成功率 | 提升 5–15 个百分点，受基线与失败构成限制 |

这些区间不适用于全部任务。业务执行占主导的长任务收益更小；已使用合并 ACK/submit
的链路也可能接近区间下沿。不能用历史小样本的成功率代表当前版本。
若协调占耗时 40%，协调时间减半才对应总耗时降低约 20%；若基线失败中只有少部分
属于协议/文件问题，总成功率不会因此提高 15 个百分点。

对照要求：

1. 固定模型及参数、资源限制、输入、验收 oracle、运行时版本和初始化方式；只变更
   公共协议实现及必要接入。基线与候选交错执行，记录失败和人工介入，不只保留成功。
2. 用例覆盖简单交付、依赖输入、并行子任务、中间产物、业务拒绝及返工、重复通知、
   传输中断、重启、取消/重新分配。每个运行时通过共同契约；另外验证代表性异构组合。
3. 端到端从原请求进入开始，到独立产物验收且原会话读到正确报告结束。记录协调/业务
   耗时分段、成功与超时、模型工具调用、输入输出 token、重试与人工介入。
4. 报告成功率分母、样本数与不确定性；耗时报告 P50/P95 和失败/超时，防止通过丢掉
   慢失败样本制造提速。小样本只用于发现问题，不用于承诺提升百分点。
5. 记录最终候选实际加载的 CLI、公共库、提示词和运行时版本，不以源码提交替代镜像验证。

## 五、实施顺序

1. 固定请求/响应、错误与产物身份契约，补充共享契约用例，采集当前 main 同条件基线。
2. 落地任务 get 与文件 list/read/get/put；复用现有鉴权与存储能力，验证边界、版本和校验。
3. 收敛 begin/submit，将现有规则接入公共任务操作，验证合并调用和失败恢复。
4. 收敛 create/plan/accept/reject/complete 与事件推进，保留原任务身份及原会话回告。
5. 全部 Harness 通过同一契约与实际打包验收，再做同构/异构对照并报告收益。

范围只包含 Task 协议与 CLI 收敛；不重构无关运行时代码、不增加另一套工作流引擎，
不把未完成的数据库迁移包装为本轮实现。新协议未验证前保持设计/实现 PR 为 Draft。
