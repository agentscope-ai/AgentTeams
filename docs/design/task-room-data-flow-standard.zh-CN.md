# 任务房间标准数据流与消息展示规范

版本：验收草案 v0.4。本文规定目标行为，已进入 Codex、QwenPaw、Claude Code、DeepSeek 的逐项本地实现与验收，不代表当前环境已经全部通过。第八节收录本轮对话和实际验证中暴露过的反例，第九节规定 Harness 接入与回归验证的使用方式。

## 一、总体流程

一个主 Task 对应一个任务房间。Leader 在任务房间完成需求分析与节点规划，发布任务概要，再开始派单。每个 Worker 的处理过程和阶段结论归为同一轮展示，交接通知单独展示。最后由 Leader 验收并完结主 Task。

```text
Leader 分析需求、规划节点与负责人
  ↓
① Leader：任务概要、要求、完成标准、执行安排
  ↓
② Leader → @首节点 Worker：派单
  ↓
③ Worker A：开始说明 → 思考/工具 → 阶段结论与产物
  ↓
④ Worker A → @Worker B：交接
  ↓
⑤ Worker B：开始说明 → 思考/工具 → 阶段结论与产物
  ↓
……按依赖继续推进……
  ↓
末节点 Worker → @Leader：请求总体验收
  ↓
Leader：核对完成标准、验收结论、完结 Task
  ↓
最终结论及选定文件回到原始会话
```

这里的顺序指用户看到的业务消息顺序。成员加入、运行状态等内部事件不单独占据业务消息位置。串行流程按上述顺序推进；并行节点由 Leader 在规划中明确，依赖满足后分别派单。

## 二、Leader：先规划，再发布概要和首节点派单

### 1. 在任务房间完成规划

原始会话用于理解请求、登记主 Task 和进入任务房间。Leader 在任务房间核对需求、确定完成标准，规划节点、负责人及依赖关系。

规划中的公开思考摘要与工具调用，归入 Leader 这一轮的过程区。规划完成后，第一条业务消息呈现为任务概要；概要与规划过程关联，不额外增加“已接收”“任务房间已创建”等独立回执。

### 2. 第一条业务消息：任务概要

Leader 完成并保存执行规划后，把概要作为这一规划轮的业务结论发布，至少回答以下问题：

| 内容 | 要说明什么 |
| --- | --- |
| 当前任务 | 本次要完成什么 |
| 任务要求 | 功能、范围、约束、必要输入 |
| 完成标准 | 用什么证据判断完成，包括测试与交付要求 |
| 执行安排 | 哪些 Worker 负责哪些节点，按什么依赖推进 |
| 最终交付 | 交付哪些文件或链接，回到哪个原始会话 |

示例：

> **当前任务：开发商品首页 HTML 页面**
>
> **目标与要求**：实现首页布局、搜索和分类交互，沿用指定仓库的页面风格。
>
> **完成标准**：页面可正常打开；搜索和分类操作通过独立测试；代码审查通过；向指定仓库提交 PR；HTML 文件交付原始会话。
>
> **执行安排**：Developer 实现 → Reviewer 审查 → Tester 独立测试 → Leader 总体验收。

任务概要是共同的阅读入口。完整原始要求仍保存在 Task 中；概要不能覆盖或遗漏原始要求。后续交接引用这一任务说明，不反复粘贴全文。

### 3. 第二条业务消息：首节点派单

概要发布成功后，任务系统代 Leader 在房间 @ 首节点 Worker：

> @Developer 请开始页面实现。按当前任务说明完成首页与交互，提交 HTML 文件及实际验证结果。

派单应说明当前节点的工作、必要输入与产物要求。概要和首节点派单必须保持先后顺序。重试不能重复创建概要、重复派单或重复唤醒。

## 三、Worker：同一轮展示处理过程与阶段结论

### 1. 收到派单后直接工作

被 @ 的 Worker 取得当前节点职责、必要上游结论及准确产物引用，开始执行。

Worker 可以自然说明“我先检查页面结构，再实现搜索交互”。这句话属于它自己的同一轮处理过程；Controller 不额外发送固定的接单确认，也不要求为了确认收到任务再触发一轮模型调用。

### 2. 进行中：展示真实过程

同一轮消息持续呈现运行时公开的思考摘要、阶段性说明和真实工具调用。工具可展开查看名称、入参、出参及状态。

不要求模型额外编造过程或增加解释轮次。工具开始、执行中、完成是同一次调用的状态变化，界面只统计一次调用。

### 3. 完成后：过程收起，结论保留

Worker 提交真实结果后，这一轮展示为：

```text
Developer
  ▸ 过程：思考摘要、工具调用、失败及重试记录

  已完成首页布局和搜索交互，并完成本地检查。
  产物：index.html。
  接下来由 Reviewer 进行代码审查。
```

阶段结论必须在折叠区外直接可见，说明实际完成的工作、验证结果、产物和下一环节。失败或受阻时，如实说明证据与缺口。

不能用“节点结果已保存”“后续由任务系统接管”等控制回执替代业务结论，也不能把业务结论连同过程一起隐藏。

### 4. 下一条独立消息：交接给下游

节点结果保存并满足推进条件后，任务系统代当前执行者发出交接：

> @Reviewer 页面实现已提交，请审查 index.html，并给出独立检查结论。

这条交接与上一条阶段结论分开展示。普通节点直接交接给下一个 Worker，不需要每一步先 @ Leader，再由 Leader 转发。

下游 Worker 同样按“开始说明 → 实际过程 → 阶段结论 → 独立交接”继续推进。每个节点只执行自己的职责。

## 四、末节点与 Leader 验收

末节点提交后，任务系统代末节点 Worker @ Leader，请求总体验收。

Leader 核对原始完成标准、各节点结论、最终产物和实际验证证据，发布明确的验收结论。报告第一句直接给出通过或需要返工，再列交付文件、必要验证证据和限制；保持简短，完整细节放报告文件，避免长表格把结论推到视窗下面。结论始终留在折叠过程之外：

- 通过：调用任务完结操作，主 Task 进入 completed，并将最终结论及选定文件交付原始会话。
- 不通过：说明具体差距，在同一主 Task 和房间内安排修正、复审或补测，保留失败记录。

执行节点全部完成，表示进入 Leader 总体验收；不能仅凭最后一条通知就把主 Task 视为完成。

### 回投来源会话（强制验收项）

任务完结后，结果必须回投最初提出需求的来源会话，不能落到任务房间、其他私聊或中间转发房间。回投必须同时满足：

1. 有实际任务结果正文：明确结论、已完成内容、必要验证证据及限制；不能只有“已完成”、任务编号或任务链接。
2. 有文件产物时，回投消息流必须展示真实、可点击的文件卡片；文件名、路径和正文中的链接不能代替文件交付。
3. 实际点击查看或下载，核对文件名、准确提交版本、字节数和 SHA256；选定最终产物必须全部送达。
4. 没有文件产物的任务仍须回投实际结果正文。回投失败或部分附件失败要保留投递状态并幂等重试，不重新执行任务，也不重复刷已投递的正文或文件。

主 Task 的业务完结与来源会话的投递完成分别验证。即使状态已是 `completed`，实际结果正文或任何选定附件尚未送达，整体验收仍未通过。

### 交付文件展示（强制验收项）

- 已提交的交付文件必须在任务房间的消息流中以真实、可点击的文件卡片展示；阶段产物关联该阶段结论，最终选定的文件同时交付原始会话。
- Matrix 原始聊天事件必须包含真实的 `m.file` 附件、文件名、媒体地址和必要的大小/类型信息，并能追溯准确的 Task、提交和产物版本。不能由 Dashboard 从文件名或路径文本猜出一张卡片。
- 在实际界面点击卡片，确认可以打开、预览或下载。对 HTML 交付还要验证实际页面能打开；不得仅凭正文出现文件名、工具返回上传成功、资产登记或 Task completed 就通过。
- 真实下载并核对字节数和 SHA256，必须与最终选定提交一致。临时文件、私有工作区路径、失效链接或旧版本不算交付；失败重试和恢复不能重复刷附件。

## 五、消息关联与上下文交接

| 标识 | 关联范围 |
| --- | --- |
| TaskId、节点 ID | 整体任务与各节点的职责、提交、状态和产物 |
| RoomId | 共同协作的任务房间 |
| RunId | 同一个 Agent 本轮的过程、工具调用和业务结论 |
| ToolCallId | 一次工具调用的名称、参数、结果及状态更新 |
| Matrix ThreadId | 房间话题与回复关系，不替代 RunId |

不同 Worker、不同处理轮次使用各自的 RunId。阶段结论与其过程共用本轮 RunId；交接保持独立消息，并关联准确的节点提交与接收者。

**下游上下文只自动携带必要信息：**任务概要引用、自己的职责与完成标准、必要上游结论、准确的产物路径和版本。完整要求、报告正文等按需读取，不复制整份房间历史、其他 Worker 的思考或工具输出。

**发送者上下文记录交接事实：**系统确认实际发送后，将“已通知哪个下游、对应哪个提交及消息”静默注入当前执行者的原生上下文并持久化，不因此再次触发推理或发一条“已通知”回执。发送尚未确认时，不能记成已经通知。

**控制数据与业务展示分开：**内部回执保留给状态校验和恢复使用；静默展示不能清空持久化结果。只有纯控制轮次静默结束，真实任务概要、阶段结论、异常说明和最终验收始终可见。

**Matrix 聊天流本身必须干净（强制）：**上述规范直接约束 Matrix 的 `m.room.message` 原始事件，不能靠 Dashboard 的关键词、角色、正则或其他过滤规则隐藏不该发送的消息来达标。内部受理、阶段完成、回执和去重事实保存在任务状态或原生上下文中；需要传输的内部控制使用明确的非聊天协议事件，不伪装成聊天气泡。真实概要、实际工作过程、阶段成果和必要的 @ 交接才进入聊天流。验收必须同时读取 Matrix 原始聊天事件和渲染结果。

## 六、职责分工

| 组件 | 职责 |
| --- | --- |
| Leader | 分析需求、规划节点、发布概要、处理异常与总体验收 |
| Worker | 执行本节点、提交真实产物和证据、说明阶段结论 |
| Controller / 任务系统 | 保存状态和提交、按依赖推进、保证消息顺序、代当前角色 @ 下游、记录真实发送事实 |
| Harness | 关联本轮过程与结论、执行控制注入、保存原生上下文、避免回执触发重复推理 |
| Dashboard | 进行中展示过程；完成后折叠过程、保留业务结论；交接通知单独呈现 |

## 七、验收清单

1. 第一条业务消息是 Leader 规划完成后的任务概要，包含要求、完成标准和分工。
2. 第一条概要发布成功后，才出现 @ 首节点的派单。
3. 每个 Worker 的开始说明、思考摘要、工具调用和阶段结论归在同一轮。
4. 完成后过程默认折叠，实际业务结论和产物引用直接可见。
5. 展开过程可查看真实工具名、入参、出参、状态及失败记录，同一调用不重复计数。
6. 普通成功节点直接 @ 下游；末节点 @ Leader；异常由 Leader 按证据处理。
7. 下游只收到必要交接信息；发送者静默记住实际发送事实，不额外推理或回执。
8. Leader 验收后主 Task 才完结，最终结论和准确文件回到原始会话。
9. 重试和恢复保留上述顺序、关联和交付事实，不重复派单、制造空消息或隐藏业务结果。

## 八、历史反例：现象、体验影响与修复检查

以下案例来自本轮用户反馈和实际验证记录。它们是必须防止再次出现的回归案例，不表示每个 Harness 都有同一缺陷，也不表示这些问题已经全部修复。已定位的原因与待查现象应分开记录，不能仅凭界面表现就归因给模型、Skill 或 Harness。

### 1. 任务开头与消息结构

#### FLOW-01：房间开头没有任务概要

- **反例**：第一条只有“任务房间已创建，请在这里规划”，随后直接 @ Developer；用户看不到当前任务、要求和完成标准。
- **体验影响**：进入房间后不知道团队在做什么，必须返回原始会话找需求。
- **正确行为**：Leader 规划后先发布完整概要，再派发首节点。
- **检查与归属**：验证首条业务消息的实际内容及顺序；由 Leader 规划输出、任务系统发布顺序和 Harness 展示共同保证。仅把建房通知换成长文案，不等于已经满足“先规划后概览”。

#### FLOW-02：在原始会话做完整规划，任务房间缺少规划上下文

- **反例**：Leader 在私聊里反复分析、拆节点、调规划工具，任务房间里只剩执行通知。
- **体验影响**：原始会话过重，任务房间无法独立说明执行安排。
- **正确行为**：原始会话整理请求并登记 Task；节点、负责人、依赖和验收安排在任务房间规划。
- **检查与归属**：同时查看两个房间的实际消息和工具所属 RunId；由 Task 阶段切换及 Harness 的房间上下文负责。

#### FLOW-03：先派单，后补概要

- **反例**：规划接口先把首节点唤醒，Leader 之后才发送任务说明；重试后又重复发一遍概要或派单。
- **体验影响**：用户看到执行先于解释，下游可能在共同要求尚未发布时已经开工。
- **正确行为**：规划保存 → 概要发布成功 → 首节点派单。失败重试沿用原身份和已确认结果。
- **检查与归属**：制造概要发送延迟或失败，验证首派单不会越过它，重试不会重复；主要归属 Controller 的发布和调度顺序。

#### FLOW-04：只有过程和流转，没有阶段成果

- **反例**：界面只有“思考 4、工具 4、失败 1”和 @ 下游，没有“实际完成了什么”。本轮 Codex 曾把真实结果替换成“节点结果已保存”，界面又隐藏该占位语，最终业务结论消失。
- **体验影响**：用户无法区分 Worker 已完成工作、只调用了工具，还是执行中断。
- **正确行为**：实际阶段结论和产物在折叠区外可见，随后再发独立交接。
- **检查与归属**：按执行者精确检查其结论文本及可见位置，不能用交接里的文件名代替。先修 Harness 的结果投影，不能继续扩大接收端关键词隐藏规则。

#### FLOW-05：过程与结论分裂，或不同 Agent 的过程串在一起

- **反例**：同一个 Worker 的思考、工具和最终结论分成多个无关联气泡；最终结论缺 RunId；只按 ThreadId 或时间邻近归并，混入另一个 Worker。
- **体验影响**：工具属于谁、结论依据什么都不清楚，过程可能被误标为未完成。
- **正确行为**：同一 Agent 本轮使用同一 RunId，并按发送者隔离；交接单独展示。
- **检查与归属**：交错发送两个 Agent 的事件，覆盖乱序、编辑和分页；Harness 发出完整关联字段，Dashboard 按统一规则归并。

#### FLOW-06：回执刷屏、Leader 自 @

- **反例**：连续出现“已接收”“开始处理”“节点已保存”“已通知下游”；Leader 被系统代发消息 @ 自己，之后又开一轮推理。
- **体验影响**：有意义的信息被挤散，用户误以为还有额外工作或新的指令。
- **正确行为**：开始说明归入 Worker 自己的同一轮；控制事件不单独形成回执气泡。任务概要、业务结论和实际交接保留。
- **检查与归属**：检查真实消息条数、@ 目标和推理触发次数；归属 Controller 控制事件及 Harness 的接收、注入和展示。

### 2. 工具、结束状态与额外推理

#### FLOW-07：工具信息只有“正在执行命令”

- **反例**：只显示 commandExecution 或工具名，没有入参、出参、错误和最终状态；Task 恢复执行没有走正常过程回调。
- **体验影响**：用户不知道实际做了什么，也无法判断为什么慢或失败。
- **正确行为**：正常执行与恢复执行都投影真实工具名、参数、结果、状态及稳定的 ToolCallId。
- **检查与归属**：分别执行正常工具、失败工具和恢复工具，展开核对真实数据；归属各 Harness 的原生回调与协议映射。

#### FLOW-08：工具重复计数，或者失败被误报成功

- **反例**：一次调用的开始和完成被算成两次；失败出参没有映射为失败；只因调用结束就显示成功。
- **体验影响**：工具数量虚高，错误证据被掩盖，阶段结论与过程矛盾。
- **正确行为**：同一 ToolCallId 更新同一调用，以实际结果判定状态。失败后修复成功时，保留失败记录，并在结论中说明最终结果。
- **检查与归属**：覆盖并发同名工具、乱序完成、非零退出码和带错误的返回；Harness 和 Dashboard 分别验证生产与归并。

#### FLOW-09：正常静默被显示成“本轮未生成最终答复”

- **反例**：纯控制阶段正常结束，却出现空过程气泡或黄色异常提示；反过来，为去掉提示又把真实中断也隐藏了。
- **体验影响**：用户把正常交接当作失败，或者看不到真正的故障。
- **正确行为**：明确区分静默完成、正常业务完成、失败和取消；真实业务结论始终可见。
- **检查与归属**：同一组测试同时覆盖正常静默、有结论、失败、取消及无终态事件，避免只验证“提示消失”；归属 Harness 终态标记和 Dashboard 呈现。

#### FLOW-10：工具已成功提交，却继续推理或重复回复

- **反例**：Task 已提交、下游也已通知，SDK 的最终答复补偿逻辑又请求模型；原生会话标题生成或入房介绍产生无关推理。
- **体验影响**：流程变慢、成本增加，出现重复结论和与任务无关的消息。
- **正确行为**：经验证的阶段完成后结束本轮；发送事实静默注入。已命名任务不因辅助标题或入房介绍增加无关工作。
- **检查与归属**：核对原生模型请求和提交、发送时间，而不是把“思考块数量”当推理轮数；归属 Harness 及上游 SDK 的结束、补偿和辅助事件路径。

- **工作目录变化的实测反例**：Claude Code Tester 在子目录运行测试后提交。Harness 使用提交当时的目录查询会话，未找到已经写入的派发事实，重试时反复追加同一个 Matrix 事件。验收需覆盖进入子目录后提交和重复检查，在最初的原生提交会话确认同一派发事件只出现一次，并核对恢复后没有新增模型调用。

- **原生会话分支的实测反例**：Claude Code 的历史查询可能漏掉已经写入的用户消息。重试时以提交会话持久化的确切发送事实去重。验收时还要恢复该会话，确认下一次正常工作能读到一次该事实，静默写入和重试期间的模型请求均为零。

- **接收者重启的实测反例**：C10 在最后一次验收通知发出后重建了 Leader。恢复同一轮验收时只需向接收者发内部事件。任务房间保留第一次公开交接；发送者的事实始终引用第一次公开发送的 Matrix 事件 ID。

#### FLOW-11：为了静默展示，把持久化交付结果也清空

- **反例**：本轮 PR25 的实跑中，规划已完成，但把空展示直接作为待保存结果；交付层要求非空回执，导致该条内部消息不能正常结束并进入重试。
- **体验影响**：后台 Task 可能继续推进，消息状态却悬挂，用户看到的完成情况与持久化事实不一致。
- **正确行为**：展示可以为空；持久化交付仍保留已验证的原始事实。两者分别保存和恢复，不改空内部回执、不绕过校验。
- **检查与归属**：完整走“原生阶段完成 → 保存交付结果 → 发布静默结束 → 确认送达”，不能只 Mock 最后的展示函数；归属 Harness。

### 3. 节点推进与任务状态

#### FLOW-12：普通节点每一步都先 @ Leader

- **反例**：Developer 完成后 @ Leader，Leader 再 @ Reviewer，Reviewer 又 @ Leader 转派 Tester。
- **体验影响**：Leader 上下文被普通转发占满，多出推理轮次，真正的异常和验收被淹没。
- **正确行为**：普通成功直接推进下游；Leader 处理异常和总体验收。
- **检查与归属**：检查交接发送者、接收者和来源提交，不仅看最终是否完成；归属 Controller 推进策略及小队 Skill 的角色职责。

#### FLOW-13：Task 登记成功，受理阶段却没有退出

- **反例**：已创建主 Task 和任务房间，但原生受理轮没有正确应用 phaseComplete/contextUpdate，规划通知在后面等待。
- **体验影响**：用户看到“已创建”，后续却迟迟不启动，重复催促还可能引发重复建单。
- **正确行为**：受理阶段按确认结果结束，规划在原 Task 房间接续，沿用已登记的来源与身份。
- **检查与归属**：从真实来源请求验证到实际规划工具调用，并重放重复投递；归属共享 Task 协议与各 Harness 的原生阶段管理。

#### FLOW-14：末节点已通知，Leader 不验收，主 Task 不完结

- **反例**：末节点已 @ Leader，但消息未被正确接收、作用域不匹配或结束状态未处理，Task 一直进行中。
- **体验影响**：用户无法判断是缺产物、等人工，还是系统卡住。
- **正确行为**：校验末节点通知并进入验收；证据不足时明确缺口；通过后真正 complete，再向原会话交付。
- **检查与归属**：同时验证通知、Leader 实际验收、主 Task 状态及原会话交付，不能以“最后一条 @ 已出现”判定成功；归属 Controller、Harness 和 Leader 验收行为。

#### FLOW-15：返工另建主 Task，或删除失败历史

- **反例**：审查失败后直接接受失败结果、跳过独立复审、重开已完成祖先，或者另建主 Task 规避原状态。
- **返工派单反例**：R27 中 Leader 已发布拒绝理由，系统却借用旧版产物提交者的身份，出现 Developer 自己 @ 自己修正。返工首节点应由作出决定的 Leader 派发；后续独立复测由实际完成修正的成员交接。旧版文件继续作为可追溯输入。
- **体验影响**：用户失去同一任务的完整过程，不知道哪份产物经过了有效审查。
- **正确行为**：同一主 Task 和房间中保留失败提交，安排修正与独立复审，下游使用准确的修正版本。
- **检查与归属**：故意提供错误产物，验证失败、修正、复审、继续执行和总体验收；归属任务状态机、Leader 及小队 Skill。

### 4. 上下文与角色权限

#### FLOW-16：关联了 Skill，实际任务上下文却没有内容

- **反例**：资产页已关联角色 Skill，新任务房间或协调会话只带元信息，模型没有获得有效内容，执行仍走旧流程。
- **体验影响**：用户以为已配置规则，实际协作却不遵守，反复改提示词也不一定生效。
- **正确行为**：按角色与任务作用域加载关联 Skill，能证明实际进入了本次原生上下文。
- **检查与归属**：核对新会话的真实输入或原生加载记录；先区分“没加载”和“已加载但规则有误”；归属 Harness 的 Skill 投影或 Skill 本身。

#### FLOW-17：每次交接重复塞整份任务和结果快照

- **反例**：上游把原始需求、完整 Task JSON、全部报告和 HTML 正文再复制给下游；节点 spec 也重复整份主任务。
- **体验影响**：上下文冗长，必要信息反而难找，推理变慢并容易读到旧版本。
- **正确行为**：保留共同任务说明，交接只带职责、必要结论及准确文件引用，正文按需读取。
- **检查与归属**：使用大报告和大 HTML 检查实际自动注入内容，而不只测空样例；归属 Controller/共享投影、Harness 与节点 Skill。

#### FLOW-18：把所有 Matrix 消息都当作当前 Worker 的输入

- **反例**：其他 Worker 的思考、工具日志、审批回执、自己发出的控制通知或定时事件进入当前业务输入，甚至触发新推理；定时事件误触发首次引导。
- **体验影响**：角色混乱、上下文污染，出现莫名回复和无关工作。
- **正确行为**：按事件类型、来源、接收者和作用域准入；业务上下文保留必要消息，控制事件只走对应控制路径。
- **检查与归属**：混合投递业务、进度、审批、定时及自发事件，核对实际模型输入和触发次数；归属各 Harness 接入层及原生事件钩子。

#### FLOW-19：已通知下游的事实没有进入自身原生历史

- **反例**：Matrix 已发送交接，发送者却不知道；或者事实只在侧车内存里，重启后再次通知、再次解释。
- **体验影响**：交接重复，用户无法判断哪一次才有效。
- **正确行为**：真实发送确认后，无推理地注入发送者原生上下文并持久化。queued 不能写成 sent。
- **检查与归属**：核对真实发送事件、原生历史与远端快照，恢复后确认没有重复发送；归属 Controller 发送事实和 Harness 的原生注入、同步。

#### FLOW-20：补充要求或人工更正在恢复后丢失

- **反例**：用户已补充验收要求，任务恢复、会话更换或配置变化后，模型只看见旧需求；压缩掉已确认的交付事实后又重复工作。
- **体验影响**：修正无效，反复解释，结果不满足用户最后确认的要求。
- **正确行为**：保留原始业务来源和有序更正，按当前兼容规则恢复必要业务上下文，不恢复过期工具授权或旧控制指令。
- **检查与归属**：在工具执行、等待审批和配置变化前后加入补充要求，再恢复验证；归属 Harness 原生会话管理与共享来源记录。

#### FLOW-21：角色权限或房间触发策略用错

- **反例**：Leader 为登记需求读取全局 Human 列表而被拒绝；或 Manager/Leader 的回复因缺少 @ 没有触发下一方。
- **体验影响**：流程悄然停住，用户误以为模型没理解或没回复。
- **正确行为**：Leader 使用自己的团队与登记用户绑定；房间按真实类型、实际参与者和授权发送者判定触发，不凭“DM”名称推定，也不扩大权限来绕过问题。
- **检查与归属**：覆盖登记用户、其他用户、两人私聊、含管理员的房间和明确 @ 场景；归属 Controller 来源/权限及 Harness 消息准入。

### 5. 审批、产物与原始会话交付

#### FLOW-22：审批看起来已同意，原生运行时却没收到有效答案

- **反例**：客户端或发送代理丢掉 com.agentteams.answer；普通“同意”文本被当作新需求，原工具仍在等待，或答案投给错误 Agent/请求。
- **体验影响**：用户反复确认，任务仍不动，还多出无关回复。
- **正确行为**：保留准确请求、上下文、目标 Agent 和结构化答案，由对应原生审批消费。
- **检查与归属**：从实际审批卡点击，经发送代理到原生工具恢复，覆盖错误目标和重复答案；归属 Dashboard、发送代理与 Harness，不能只测单侧序列化。

#### FLOW-23：审批已过期，或者等待时间耗尽执行预算

- **反例**：批准旧请求没有效果；审批卡已取消仍像待处理；人工等待后工具刚开始，整轮立即超时。
- **体验影响**：用户操作无效，难以区分等待、过期、失败和执行中。
- **正确行为**：使用当前有效请求；准确显示等待及终态；区分审批等待与工具/整轮执行预算。恢复不重放过期授权。
- **检查与归属**：延迟回答、过期回答、取消后回答及恢复分别测试，保存实际时间证据；归属 Harness 原生等待/超时和 Dashboard 状态。

#### FLOW-24：写了文件或做了私有备份，却没有交付共享产物

- **反例**：文件只存在 Worker 私有工作区或配置备份前缀，消息却宣称已经交付；路径提示矛盾，文件写进嵌套的错误目录。
- **体验影响**：下游与用户都拿不到文件，完成声明失去可信度。
- **正确行为**：按 prepared Task 的准确输出目录和提交协议交付；普通共享发布与私有备份区分。
- **检查与归属**：用下游身份读取准确版本，核对实际内容；仅 CLI 退出码为 0 不足以证明工具返回成功。归属 Harness/公共文件工具及路径 Skill。

#### FLOW-25：漏传上游文件，脚本只能在原 Worker 运行

- **反例**：Tester 只提交新报告，没转交最终所需的上游 HTML/脚本；测试硬编码另一 Worker 的私有输入路径。
- **体验影响**：任务房间里声称测试通过，用户下载文件后却无法复现。
- **正确行为**：转交最终交付所需的准确文件，保持不可变输入；脚本能在仅有选定产物的目录运行。
- **检查与归属**：下载最终选定文件，在干净目录重跑，并验证上游文件未被修改；归属小队交付 Skill 和产物引用，框架路径错误则修框架。

#### FLOW-26：Task 已完结，原始会话没有正确结果或附件

- **反例**：只在任务房间发链接；交付到错误房间；选中旧版本文件；报告与附件版本不一致。
- **体验影响**：用户在最初下发需求的位置拿不到最终成果。
- **正确行为**：沿最初来源路由回投真实任务结果正文，明确结论、完成内容和必要证据；有产物时同时展示真实可点击文件卡片，交付准确选定的版本。不能只回“已完成”或任务链接。业务 completed 与回投送达分别验收。
- **检查与归属**：在最初来源会话核对真实结果正文、实际点击卡片并下载附件，校验文件名、Task/提交身份、字节和哈希；覆盖无文件、有文件、部分失败与重试。未送达时不以 completed 冒充整体通过。归属 Controller 最终路由、版本选择和 Harness 交付。

### 6. 环境与验收方法本身

#### FLOW-27：工具协议失败，却只留下一个空过程

- **反例**：原生工具 schema、工具名或参数不匹配，XML/文本没有转换成有效调用，实际上没执行工作；重复会话标题冲突也可能在工具前终止。
- **体验影响**：用户只看到思考或无输出，不知道失败发生在哪一步。
- **正确行为**：真实协议失败可见且保持失败状态，使用原生工具注册和调用路径，不把未执行的文本当作成功工具结果。
- **检查与归属**：通过实际 SDK 覆盖合法、非法调用及重复任务，核对真实工具执行证据；归属 Harness/原生 SDK，不能只靠提示词规避。

- **超时后仍执行的反例**：Claude Code 的 Tester 请求前台执行检查。原生工具在超时后返回后台任务 ID，模型随后又发起多次调用，每次都被未确认的操作挡住。只有同步执行能力的 Harness 应禁用自动转后台；遇到缺少终态的返回，记录一次待核对原因，停止本轮并保留原操作。回归时核对工具结果、原生检查点和后续模型请求数，确认没有重放已产生的副作用。

#### FLOW-28：源码、CLI、镜像或前置配置未对齐

- **反例**：镜像携带旧 agt；入口路径错误；文件工具没有执行权限；模型不可用、仓库不可访问，却开始派单或报告环境就绪。
- **体验影响**：表面像协作卡住，实际业务工具尚未具备执行条件。
- **正确行为**：区分源码修复、镜像构建、实际部署和运行验证；按执行角色验证所需模型、仓库与工具能力。
- **检查与归属**：核对实际运行镜像与源码、CLI 版本/哈希及真实调用结果。环境组装问题修环境，Skill 问题修 Skill，不混为状态机缺陷。

#### FLOW-29：把过程块或诊断 Span 数量当成模型调用数量

- **反例**：模型配置读取、响应片段被 Tracing 后端算作 GENERATION；把“思考 17”直接解释成额外推理 17 次；筛选失效返回其他任务的追踪。
- **体验影响**：用户误判耗时、成本和重复执行原因，排障方向错误。
- **正确行为**：区分过程片段、工具调用、原生模型请求和辅助 Span；追踪按真实 Worker/Task/Run 范围查询。
- **检查与归属**：核对原生请求边界、类型、父子关系和时间；不能删除真实 Span 来修正计数。按证据定位 Harness、Collector 或查询层。

#### FLOW-30：测试宣称通过，真实消息流仍不符合标准

- **反例**：只断言任务 completed、房间出现文件名、共享库测试通过或截到局部页面。R24 的任务状态和文件交付通过，但用户截图仍没有 Developer 的业务结论；文件名实际可能只出现在派单里。
- **体验影响**：用户反复指出同类问题，测试无法保护真实体验。
- **正确行为**：分别证明实际执行、消息结构、可见结论、原生上下文、状态和文件交付；一层通过不能替代另一层。
- **检查与归属**：用精确发送者和实际结论定位结果消息，验证折叠后的可见内容。人工补发指令、改镜像、补依赖后的恢复须记录为有干预；其他 Harness 未原生验证或明确跳过时，不得宣称全部通过。归属测试与验收流程。

#### FLOW-31：用 Dashboard 隐藏规则掩盖 Matrix 消息污染

- **反例**：Controller 或 Harness 仍然发送“节点已保存”“已处理”或完整内部回执，再由 Dashboard 的关键词、正则、角色或静默标记过滤；换一个 Matrix 客户端就看到脏消息。
- **体验影响**：网页看似干净，Matrix 实际聊天流、搜索、其他客户端和后续上下文仍被冗余消息污染。
- **正确行为**：发送端不生成多余聊天消息；持久化控制事实与对外业务消息分开。正常过程按 RunId 聚合，内部控制走非聊天协议；不删除或遮蔽真实业务成果和故障。
- **检查与归属**：直接读取新 Task 的原始 `m.room.message` 列表，确认没有控制回执、占位结论或 Leader 自 @，再检查界面；不能以 Dashboard 隐藏成功作为通过。归属 Controller/Harness 发送端，Dashboard 只负责正常过程归并和折叠。

#### FLOW-32：交付物只有文件名，消息里没有可点击附件

- **反例**：阶段结论或最终报告写着 `collaboration-preview.html`、`test-report.md`，但任务房间没有文件卡片，用户无法点击查看；R25 原会话已有附件，任务房间仍只有文件名。
- **体验影响**：用户看见“已交付”却拿不到产物，无法验证阶段结果，也无法区分正确版本与旧文件。
- **正确行为**：发送端将已提交、已校验的准确产物作为真实 Matrix 文件消息，关联对应阶段结论；最终选定文件还需送达最初会话。文件名文本或资产条目不能替代附件。
- **检查与归属**：同时检查任务房间和原始会话的原始附件事件、实际可点击卡片、打开/下载行为及字节哈希；覆盖部分上传失败、重试和版本选择，确认不漏传、不重复。归属 Controller/Harness 的产物发送；若已有合法附件但无法操作，再修 Dashboard 的文件查看链路。

- **来源会话有并发消息时**：在同一个 Leader 的过期审批卡片后插入真实验收结论和两个附件。检查审批卡片和报告分别展示，文件跟随报告。C8 曾把报告并入上一张审批卡片，原始 Matrix 已送达，用户仍看不到文件。

## 九、Harness 接入和回归测试怎样使用本规范

### 1. 接入前必读，按案例编号记录结果

新 Harness 接入，以及修改收发消息、Task 阶段、Skill 注入、会话恢复、过程展示或产物交付时，先对照第八节识别受影响案例。各运行时共用同一行为标准，不为某个 Harness 放宽标准。

验证记录至少包含：案例编号、源码提交、实际镜像、Harness、Task/Room/Run 标识、复现操作、期望与实际结果、证据、结论和修复归属。结论使用“通过／失败／未验证／按用户要求跳过”，不能把“没有报错”记成通过。

### 2. 最低场景矩阵

| 场景 | 必须核对的行为 | 关联案例 |
| --- | --- | --- |
| Leader 受理与规划 | 原会话轻量受理；任务房间先概要后派单 | FLOW-01～03、13 |
| 单节点到总体验收 | 同轮过程与真实结论；末节点通知后 Leader 验收和完结 | FLOW-04～06、14 |
| 多节点及交错消息 | 直接交接、各 Agent 隔离、必要上下文 | FLOW-05、12、17～19 |
| 审查失败与返工 | 同一 Task 保留失败、修正和独立复审 | FLOW-08、15 |
| 静默与真实故障 | 正常静默不报警，真实故障不隐藏，交付事实不清空 | FLOW-09～11 |
| 审批、停止和继续补充 | 精确控制目标、有效审批、无重复执行、补充不丢失 | FLOW-20、22～23 |
| 重启或会话恢复 | 恢复业务来源、提交和发送事实，不重复派单或推理 | FLOW-10～11、19～20 |
| 大任务和大产物 | 引用读取、上下文不重复膨胀，最终选定文件可复现 | FLOW-17、24～26 |
| 原生协议与环境 | 实际工具能执行，运行源码和镜像一致，追踪计数准确 | FLOW-07～08、16、21、27～29 |
| 最终用户视角 | 完整消息顺序、默认折叠后的结论、两处可点击文件卡片与真实下载均正确 | FLOW-30、32 |

### 3. 测试必须看到真实业务结论

不能仅断言 `body` 中出现文件名或“通过”。至少证明：

1. 该结论来自准确的执行者、Task 节点和本轮 RunId，而不是派单、交接或工具内部回执。
2. 页面默认折叠过程时，实际阶段结论和产物引用仍在折叠区外可见。
3. 展开后能看到同一轮的真实思考摘要和工具名、入参、出参、状态；无其他 Agent 的过程混入。
4. 消息顺序满足概要 → 首派单 → 节点处理与结论 → 下游交接 → 总体验收。
5. 已提交的交付文件在任务房间消息中有可点击卡片，最终选定文件同时送达原始会话；实际点击打开或下载，并核对内容与准确提交版本一致。

### 4. 遇到反例时的处理规则

验收最后一轮时，截图必须覆盖折叠过程之外的验收正文和产物信息。不能仅凭 DOM 里存在文本判定实际可见，也不能把只截到过程栏的阶段截图当作完整收尾证据；先核对原始 Matrix 事件和实际滚动区域，再判断结果是否丢失。

先保留实际失败记录与复现证据，再确定修复归属：共享推进与顺序修 Controller，原生回调和上下文修 Harness，渲染归并修 Dashboard，业务职责或测试方法修对应 Skill，部署不一致修环境。

修复需要有能在修改前暴露问题的回归，并在修改后验证相同场景。记录到反例清单不等于已经修复；后续代码、测试和验收记录应引用案例编号。不得只隐藏消息、清空状态、另建任务或改小验收范围来制造通过。
